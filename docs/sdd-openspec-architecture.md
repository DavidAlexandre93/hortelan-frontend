# SDD Architecture With OpenSpec

This repository uses OpenSpec as the spec-driven development layer for product, architecture, reliability, security, and delivery changes.

## Repository Layout

- `openspec/config.yaml`: project context, artifact rules, and apply/archive guidance for AI agents.
- `openspec/specs/`: source-of-truth behavior specs, grouped by domain.
- `openspec/changes/`: active change proposals created by OpenSpec workflows.
- `.agents/skills/openspec-*`: Codex-compatible OpenSpec workflows generated by `openspec init --tools codex`.

## Current Capability Map

- `architecture/sdd-governance`: SDD process, validation, and archive rules.
- `architecture/frontend-app-shell`: splash, routing, route protection, lazy loading, and selective SSR.
- `identity/auth-session`: backend-first auth, demo fallback, MFA, trusted devices, sessions, and privacy controls.
- `platform/api-reliability`: API base URL resolution, timeouts, retries, error normalization, and metrics.
- `delivery/frontend-quality`: OpenSpec validation, quality gate, build, bundle, performance, and deployment promotion.

## Daily Workflow

Use the generated Codex OpenSpec skills after restarting the IDE:

1. Explore uncertain work with `$openspec-explore`.
2. Create a proposal with `$openspec-propose "change description"`.
3. Review `proposal.md`, delta specs, `design.md`, and `tasks.md`.
4. Implement with `$openspec-apply-change`.
5. Validate with `npm run openspec:validate` and the affected project checks.
6. Sync or archive completed work with `$openspec-sync-specs` and `$openspec-archive-change`.

## Local Commands

```bash
npm run openspec:list
npm run openspec:doctor
npm run openspec:validate
npm run openspec:update
npm run quality:gate
```

`quality:gate` includes OpenSpec validation so malformed specs fail beside lint, format, tests, build, and frontend audit.

## Change Rules

- Add or modify specs for behavior-changing work before editing implementation code.
- Use `skip_specs: true` only for pure tooling, docs, or refactors with no behavior change.
- Keep requirements observable and testable; implementation details belong in `design.md` or `tasks.md`.
- Archive completed changes so future agents inherit source-of-truth specs instead of chat history.
